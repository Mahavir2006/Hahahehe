# Architecture — CascadeShield

## Overview

CascadeShield is a cross-organisation cascade-risk prediction system for critical infrastructure. Three mutually distrusting organisations (power, water, hospital) each run their own agent node with private data. They coordinate only through a permissioned local EVM blockchain that stores hashes, commitments, attestations, approvals, and alerts — never raw inventories or sensitive asset data. Values that would tell a chain reader *what is vulnerable* (risk bands, dependency terms, alert severity, finding outcomes) are only commitments on-chain; members exchange the values as sealed envelopes encrypted to each other's `OrgRegistry` keys (`backend/common/sealed.py`, SEC-PRIV).

## Layered Architecture

### 1. Data Layer (`data/`)
Deterministic simulated data generated by `data/generate_dataset.py` with seed 42:
- `orgs/{power,water,hospital}/inventory.json` — 20-30 assets per org
- `orgs/{power,water,hospital}/services.json` — services mapped to assets
- `orgs/{power,water,hospital}/private_keys.dev.json` — dev keypairs (admin, agent signer, 3 approvers)
- `cross_org_dependencies.json` — bilateral dependency edges incl. power→water→hospital
- `advisories/*.txt` — ≥12 messy advisory texts incl. 2 prompt-injection samples
- `firmware_catalog.json` — vendor firmware with SHA-256 hashes
- `historical_incidents.csv` — ≥5,000 synthetic rows for the risk model

### 2. Blockchain Layer (`chain/`)
Six Solidity contracts on a local Hardhat network (chain ID 31337):

| Contract | Purpose | Key Requirements |
|---|---|---|
| `OrgRegistry` | Org identity, roles, agent signers, approvers, thresholds | BC-ORG-01..07 |
| `AuditLog` | Append-only hash-chained audit log with Merkle batches | BC-AUD-01..08 |
| `AttestationRegistry` | Dependency, risk, and finding attestations (EIP-712 signed) | BC-ATT-D/R/F, BC-ATT-X, BC-SEC-08 |
| `FirmwareRegistry` | Vendor firmware integrity registry | BC-FW-01..07 |
| `ApprovalGate` | Non-bypassable human-in-the-loop approval gate | BC-GATE-01..15 |
| `AlertBus` | Cross-org early-warning alert bus | BC-ALERT-01..06 |

### 3. Backend Layer (`backend/`)
Python async agent runtime:

- **`common/`** — Chain client/writer (web3.py), EIP-712 signing, canonical JSON, Merkle trees, config
- **`graph/`** — IntraOrgGraph (per-org dependency propagation), CrossOrgGraph (cross-org cascade from public attestations only)
- **`agents/`** — IntakeAgent → RiskAgent → CascadeAgent → PlannerAgent → CriticAgent → ExecutorAgent, plus Orchestrator and OrgNodeRuntime
- **`risk/`** — Risk scoring model, SHAP factors, what-if analysis
- **`api/`** — FastAPI with SSE, org-scoped endpoints
- **`tests/`** — Pytest unit, integration, and lifecycle tests

### 4. UI Layer (`cascade_ui/`)
React + Vite + TypeScript. Eight sections (overview map, assets, risk prediction, cascade simulator, proactive
scenarios, recommendations, incident response, audit trail) on simulated demo data; not yet connected to the API.
The cross-language canonical JSON helper used by the chain tests lives in `shared/canonical.ts`.

## Data Flow

1. **Advisory ingestion** → IntakeAgent parses, matches inventory, publishes FindingAttestation on-chain
2. **Risk scoring** → RiskAgent calls deterministic model, publishes RiskAttestation on band change
3. **Cascade** → CascadeAgent runs intra-org + cross-org propagation (confirmed attestations only), publishes AlertBus alerts above threshold
4. **Planning** → PlannerAgent builds constraint-respecting plan with deterministic risk-reduction accounting
5. **Critique** → CriticAgent independently re-validates; verdict anchored on-chain
6. **Approval** → ApprovalGate requires human approver votes (MEDIUM: 1, HIGH: M incl. safety officer)
7. **Execution** → ExecutorAgent verifies gate on-chain, applies simulated actions, marks executed on-chain
8. **Audit** → All traces anchored via AuditLog hash chain + Merkle batches

## Trust Boundaries

- **No org sees another org's private data** — enforced by PrivateStore isolation (AG-TOP-05) and API org scoping (API-02)
- **No agent can execute without approval** — GateViolation enforced in ExecutorAgent and ApprovalGate contract
- **No agent can approve its own requests** — ApprovalGate rejects agent signer as voter (BC-GATE-06)
- **No LLM computes authoritative risk** — all numbers from deterministic model; LLM only writes narratives (AG-RSK-02)
- **Cross-org cascade uses only on-chain attestations** — engine never reads private inventory (CAS-02); it opens the sealed bands/terms addressed to its org and checks them against the on-chain commitments
- **Chain readers learn no vulnerabilities** — commitments + fixed-size sealed envelopes only (SEC-PRIV, THREAT_MODEL T-12)
